# ADR-006：真实产品优先路线与多语言成熟度门

status: accepted
date: 2026-07-26
accepted_at: 2026-07-29T06:52:10Z
task: TASK-012
supersedes_in_part: ADR-003 implementation ordering and ADR-005 decision 6

## 背景

TASK-001 至 TASK-011 已交付 Headless WordPress + Next.js、英语 SCF/Schema 3、REST-first 合同、前端 `/resolve` 快照、Transport、Runtime Validator、Adapter 和真实 WordPress 技术集成闭环。当前主要风险已经从“链路能否工作”转为“真实 GDHE 产品是否适配、IA/URL/CTA 是否正确、正式模板能否同时满足 SEO/可访问性，以及 Preview/cache/Webhook/Staging 是否支持生产编辑和发布”。

ADR-003 的小批次验收仍有效，但其历史阶段描述可能被解释为先做孤立全局壳层和首页。ADR-005 把多语言 PoC 绑定到生产英语站连续稳定三个月；该时长可以保留为风险证据，但不能代替产品、URL、Schema、发布、内容、兼容、SEO、RTL、运维和治理成熟度。

## 决策

1. 保留 TASK-001 至 TASK-011 的全部已接受架构与交付，不重选 Next.js、WordPress `wp-admin`、SCF、REST-first 或 server-only 消费边界。
2. `docs/architecture/headless-wordpress-nextjs-contract.md` 第 14 节仍是后续实施顺序的单一权威；TASK-005 保留为历史合同和交接边界，不回写归档任务。
3. 后续顺序改为：
   1. 英语站 IA、10～20 个真实产品映射、业务规则确认、URL/CTA 与内容缺口；
   2. 2～3 个真实产品纵向切片形成视觉和首模板基线；
   3. 部署拓扑/Staging、Preview、最后成功缓存、Webhook 和联合演练；
   4. 受控全局壳层；
   5. 完整产品分类/系列/详情系统；
   6. 正式首页；
   7. 其余模板；
   8. 询盘、CRM/协作、分析和隐私；
   9. 上线加固；
   10. PoC 进入门后的隔离验证，以及生产成熟度门后的逐语种建设。
4. 技术 SEO、可访问性、状态码、媒体和 URL 生命周期从首个正式模板进入完成定义；内容 SEO 随真实产品、市场、关键词和审核文案持续迭代。
5. 阶段 2 是少量代表产品的端到端证明；阶段 5 是将已证明模式扩展为完整产品系统。产品系统先于正式首页。
6. 多语言不再仅以固定三个月为启动条件。生产监控时长保留为风险证据；产品/内容、IA/URL、Schema、发布、PoC 兼容结论、语言质量、SEO、RTL/可访问性、运维和治理门必须在生产采购或公开建设前同时通过。
7. 最小多语言 PoC 必须由独立任务授权，在隔离、身份保护、`noindex`、可清理环境执行；它不构成 WPML/ACFML 采购、安装、生产兼容、公开路由或九语言上线授权。
8. PoC 进入门与生产成熟度门分开：合法许可路径、受控 Fixture、隔离环境、身份保护、失败停止和回滚计划是 PoC 前置；SCF + WPML/ACFML 兼容性 PASS 是 PoC 输出，也是生产采购和公开发布前置，不得循环要求在 PoC 前已存在。
9. TASK-007 Schema 3 是已经交付的技术合同基线，不是 GDHE 真实产品业务模型的最终冻结。TASK-012 使用测试产品记录确认业务合同和预期行为，不把测试值当作最终生产目录。10～20 个合法、可使用、来源可追溯且由业务责任人确认的最终生产产品数据验收，是正式批量导入、产品模板业务冻结和 Schema 业务冻结前的强制后续门；该门不要求 TASK-012 为收口路线图而伪造生产数据。
10. 飞书多维表格是型号、Article Number、规格和可用状态的结构化产品主数据权威；WordPress `wp-admin` 是营销文案、SEO、公开媒体和页面编排的内容管理权威。飞书主数据字段在 `wp-admin` 中可见但只读，只能在飞书修改。产品读取拓扑冻结为“飞书产品主数据 → 受控同步 → WordPress 只读镜像 → GDHE REST API → Next.js”，不默认双向同步，也不让公开页面按请求直接读取飞书。飞书必须提供显式的网站发布资格；只有被业务方标记为“允许发布”且 Article Number 有效的真实记录才有资格进入同步范围，其他记录默认排除。首次同步只创建 WordPress 草稿并由编辑人员手动发布；已发布产品的普通主数据更新通过校验后自动同步并保持公开。Article Number、型号归属、产品记录删除或撤销网站发布资格属于重大变更，进入例外审核，不自动覆盖或下线；校验失败时保留最后成功公开数据。停产产品保留原 URL 和公开页面，标记 `Discontinued`，有替代型号时展示链接，并将常规询价 CTA 改为 `Contact Us for Replacement`。quotation request 通过独立受控入口写入飞书，由业务员在飞书报价；它不反向修改产品主数据。真实字段映射、权限、重大变更处置、幂等、失败恢复和同步日志仍需独立任务确认。
11. 产品与产品系列、产品与应用场景均为多对多关系。系列和应用页面是同一产品的发现入口，不创建重复产品记录；一个产品保持单一身份、单一 canonical 详情页，并复用同一组规格与 Article Number。
12. 技术参数必须结构化保存分组、名称、值、单位和显示顺序。第一阶段统一采用公制单位，不执行面向不同市场的英制自动换算；未来换算必须保留原始标准值并另行验证。
13. 网站内容层只保存当前有效产品资料；每份当前文件记录类型、版本号、语言和生效日期，并可关联多个产品。失效旧版本只归档于极空间，不在 WordPress、飞书网站镜像或公开媒体中重复保存；极空间不进入公开 API 和网站同步路径。
14. 成本、采购价、内部销售底价、利润/利润率、供应商信息、库存数据、客户专属报价、内部备注和业务审核记录只保存在飞书多维表格，不属于网站内容或产品镜像。未来同步必须采用明确的公开字段白名单，从源头排除这些字段；它们不得进入 WordPress、GDHE REST API、Next.js、公开缓存或应用日志。WordPress 只保留自身对公开文案、SEO、图片和页面模块的编辑修订历史，不复制飞书业务审核记录。第一批公开字段已由第 15 项确认；真实 Base 映射和 B2B 扩展字段仍需逐项确认。
15. 第一批官网公开产品字段白名单包括：产品名称、型号、Article Number、真实可选规格、尺寸、颜色、表面处理、技术参数、安装方式、兼容关系、在售/停产状态、产品图片和当前有效资料。字段具备公开资格不等于自动公开；记录仍须通过飞书“允许发布”资格、数据校验和 WordPress 独立发布门。真实 Base 字段映射和代表产品取值仍需后续验证。
16. B2B 公开信息采用分层规则：MOQ 不在官网特别展示，如内部需要只保留在飞书；整柜交期是公司级通用政策，公开口径为“收到客户定金，并确认订单、包装和生产资料后，通常为 `30–40 天`”；包装材料选项按产品类别维护，每类可选材料相对固定；所有产品均可提供样品；公司可提供 OEM 和 ODM。包装类别与可选材料、交期、样品和 OEM/ODM 均由 WordPress 作为唯一编辑权威，不进入飞书产品主数据同步；当前已知产品类别的包装合同已确认，真实产品记录分配留待代表样本核对。
17. 用户提供的飞书字段截图和业务说明确认轨道类存在六个包装相关来源标签：常规、纸盒、打字、套袋、大收缩膜、对扣。官网由 WordPress 保存面向客户的详细说明；其中“打字”表达的是客户 Logo 印刷，不得在英文官网按字面翻译。轨道组合合同拆为三个维度：基础包装必须在常规/纸盒/大收缩膜中三选一；Logo 印刷是可选开关；保护/排列方式可不选，选择时只能在套袋/对扣中二选一。Logo 印刷与任一合法基础包装及保护/排列状态兼容。真实轨道记录分配仍需代表产品核对。
18. 第 17 项包装合同不适用于布带和用户所称“线珠”。这两类产品的公开常规包装是纸箱包装；特殊“组合包装”只由业务员针对已有需求的客户线下提供，不在官网展示，也不作为公开 RFQ 自助选项。同名“常规包装”在轨道类与布带/线珠类含义不同，后续模型必须使用产品类别限定的包装身份，不得合并为一个全局通用选项。封口、走珠、顶码、墙码等小型配件的包装规则仍待确认。
19. 同款、同型号且出厂配套的电机和遥控器采用固定纸箱包装。官网只展示这一固定包装事实，不提供包装选项，也不把它们接入轨道或布带/线珠的包装选择合同。
20. 轨道封口、走珠、顶码、墙码等不单独建页的小型相关配件同样采用固定纸箱包装。官网不提供包装选择，也不接入其他类别的包装合同。
21. 网站产品领域只保留一个统一的“配件”业务角色，不再建立“备件”或“套装成员”独立角色。配件通过可筛选的“配件类别”分类；当前类别示例包括顶码、墙码、走珠、封口、布带和线珠。配件角色、配件类别和公开页面身份相互独立：布带、线珠等仍可建立独立详情页，顶码、墙码、走珠、封口等仍可只作为相关配件展示。用户确认本轮“强码”是“墙码”的笔误，系统只保留“墙码”一个规范类别。
22. 配件与配件类别采用多对一关系：每个具体配件必须且只能属于一个配件类别，同一个配件 Article Number 不得同时归入多个类别；一个配件类别可以包含多个配件。配件是否还具有独立型号仍待确认。
23. 配件不强制“一件一个独立型号”。布带采用“型号 → 多个可订购规格/Article Number”的层级：钉子材质变化会改变型号，不锈钢钉与铝钉分别属于不同型号；同一型号下可因宽度、钉距和长度不同形成多个独立 Article Number。已知宽度包括 30mm、45mm、60mm，钉距包括 125mm、145mm、165mm、170mm 及更多值，长度包括 30m、40m、50m、60m 等。除布带和线珠外，封口、顶码、吊码、走珠等配件通常同时具有型号和独立 Article Number，但“通常”不是全局必填约束，真实例外须由代表样本验证。
24. 布带型号由“颜色 + 钉子材质”共同决定。例如黑色不锈钢钉、黑色铝钉、白色不锈钢钉、白色铝钉分别属于不同型号；宽度、钉距和长度不改变型号，只用于确定该型号下的具体规格及独立 Article Number。宽度和钉距统一使用毫米（mm），长度使用米（m）。
25. 线珠型号由“颜色 + 具体珠型”共同决定。当前珠型分为尚飞大方珠系列（单扣尚飞大方珠、双扣尚飞大方珠、大圆扣尚飞大方珠）和用户所称佳丽斯中方珠/珠系列（单扣佳丽斯中方珠、双扣佳丽斯中方珠、小圆扣佳丽斯珠）。型号下按珠距细分，常见珠距为 6cm、6.6cm、7cm、8cm、10.2cm；10.2cm 一般用于双扣，但当前不得建成排他约束。珠距和卷长共同确定具体可订购规格：不同珠距或不同卷长均产生独立 Article Number，但都不改变型号。
26. 同款、同型号且出厂配套的电机和遥控器继续共用一个公开产品页面，但它们是两个独立可识别部件，各自保留全公司唯一的 Article Number；不创建额外的组合 Article Number。
27. 在上述共用页面中，电机和遥控器作为两个独立 RFQ 行项目：客户可以只选择电机、只选择遥控器或同时选择两者；两者分别填写数量，数量可以不同，并各自保留自己的 Article Number。
28. 每一个加入 quotation request 的产品或配件 RFQ 行项目都必须填写数量；不存在“先不填数量、由业务员后续补录”的公开提交路径。数量的单位来源和输入格式仍待确认。
29. 官网 RFQ 使用客户易理解的订购单位：轨道按“支”、布带和线珠按“卷”、电机、遥控器及其他配件按“个”。报价进入飞书后，轨道、布带和线珠根据具体 Article Number 对应规格换算为总米数，配件继续按个计算；飞书报价系统还根据包装方式折算轨道、布带/线珠和小配件的包装件数。这些米数与包装件数属于内部报价计算结果，不要求客户在网页端填写。每个 Article Number 的换算系数由何处权威维护仍待确认。
30. 每一条飞书产品主数据记录保存该可订购产品对应的长度换算字段。报价系统只接收所选 Article Number 和客户数量，从飞书产品主数据读取该字段并计算总长度；换算公式、包装件数计算和报价实现属于飞书系统责任，不进入官网、WordPress、GDHE REST API 或 Next.js 的实现范围。业务与网站统一使用 `Article Number`；本轮曾出现的 `Part Number` 是口误，不创建该字段、别名或第二套编号。
31. 所有官网 RFQ 行项目的数量只能是大于零的整数，最小值为 `1`；空值、`0`、负数和小数均为无效输入。该约束适用于轨道“支”、布带/线珠“卷”以及电机、遥控器和其他配件“个”。
32. 英语站统一主询价 CTA 文案为 `Request a Quote`。不得在同一主转化路径中混用 `Ask for Quotation`、`Get a Quote` 等其他主按钮标签；停产产品已确认的 `Contact Us for Replacement` 例外继续保留。
33. 正常在售产品点击 `Request a Quote` 后，先把当前已选 Article Number、规格/选项和数量加入多产品询价清单；客户可以继续浏览并添加其他产品，最后在统一询价步骤填写联系信息并一次提交。不得把每次产品 CTA 点击都直接变成单产品表单提交。
34. 询价清单行身份由 `Article Number + 完整公开配置` 共同决定。重复加入同一 Article Number 且包装、Logo、套袋/对扣等全部公开配置完全相同时，合并为一行并累加数量；只要任一公开配置不同，即使 Article Number 相同也必须保留为独立行，避免丢失客户的分批或不同包装需求。
35. 型号级产品关联关系只在飞书维护。新增或删除关系后，下一次完整成功同步原子替换 WordPress 只读镜像、GDHE REST API 和产品详情页中的公开关系集合；WordPress 不重复编辑。同步失败保留最后一次成功集合，不展示半更新状态。
36. 飞书关系目标停用、撤销“允许发布”或 WordPress 未公开时，公开站隐藏该推荐且不生成指向未公开目标的卡片或链接，但保留飞书内部关系；目标重新满足资格并公开后自动恢复。
37. 官网产品媒体使用业务方预制的 `公开保护图`，包含可见水印、品牌标识或品牌底纹，并可包含型号和尺寸标注。WordPress 只管理和发布保护成品图，网站不自动加水印或排版。内部无水印原图只保存在飞书、极空间等内部系统，不进入 WordPress、GDHE REST API、Next.js、隐藏字段、构建产物或公开缓存。

## 19/16 合同口径

- TASK-007 CMS 权威交付从 page、collection、navigation、route-manifest 和 error 五个根递归解析得到 19-file Schema graph。
- TASK-008/010/011 的前端本地消费者只冻结 page + error 的 16-Schema `/resolve` closure。
- CMS 独有的三份根 Schema 是 `collection.v3.schema.json`、`navigation.schema.json` 和 `route-manifest.schema.json`；前端闭包没有额外文件。差异表示消费范围不同，不表示合同丢失，也不授权扩张当前消费者。

## 参考与内容权威

- GDHE 真实资料是产品事实、文案、媒体、下载和业务 CTA 的唯一权威。
- 产品型同业只用于目录和技术信息组织研究。
- RapidDirect 只用于信息节奏、信任、交互、响应式与转化模式研究。
- 不复制参考站品牌、源码、主题、型号、文案、媒体或未授权资产。

## 非授权

本 ADR 不授权采购、安装、真实产品导入、飞书连接或修改、CMS/Schema 修改、页面或 SEO 实现、Preview/cache/Webhook、Staging/生产部署、询盘/分析、多语言、提交、推送、合并、验收或关闭。所有候选阶段仍需独立任务和明确确认。

本 ADR 也不把产品类别清单、当前测试记录、同业参考或 Fixture 当作最终生产产品数据。测试记录只能证明经过用户确认的业务合同和预期行为；生产数据验收门详见 `TASKS/ARTIFACTS/TASK-012/REAL_PRODUCT_VALIDATION_GATE.md`。

## 状态门

本 ADR 在 TASK-012 独立审查和用户正式验收前保持 `proposed`。验收后才正式替代 ADR-003 的后续阶段顺序解释和 ADR-005 第 6 项的固定日历触发条件；ADR-003 的参考边界/小批次门、ADR-005 的英语优先/SCF/WPML+ACFML 候选边界继续有效。
